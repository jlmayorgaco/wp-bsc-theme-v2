## Antes de permitir pedidos reales

1. **Core y plugins:** inventariar versiones del VPS. Local pasó de WordPress 6.9.1 a 7.1.2 tras crear un dump verificable de la base, fuera del webroot. La versión 7.1.2 se publicó el 22/09/2026 con una corrección crítica: bajo ciertas condiciones, un atacante no autenticado podía forzar la resolución de plantilla para incluir un archivo PHP legible fuera del tema y llegar a RCE. No se ha verificado qué versión corre el VPS. **Comprueba y parchea el core del VPS en staging antes de abrir pedidos**; repite compra, callback, login, devolución y cron allí. Verifica checksums y diferencias locales del plugin Wompi. [Aviso oficial de WordPress 7.1.2](https://wordpress.org/news/2026/09/wordpress-7-1-2-release/).
2. **Wompi:** comprobar modo, claves pública/privada y secreto de eventos correspondientes al mismo entorno; realizar una compra sandbox desde el widget, verificar callback y retorno, repetir callback y probar declinación/reintento y pago posterior a vencimiento de reserva. Confirmar monto/moneda/transacción en HPOS, un descuento de stock y una acreditación de puntos. El adaptador falla cerrado si falta el secreto.
3. **DB:** comprobar InnoDB en `posts`, `postmeta`, `usermeta`, tablas HPOS, líneas/metadatos de pedido y `bsc_points_ledger`; permisos GET_LOCK y transacciones en la misma conexión. La versión de ledger es 1.1.0 y añade `event_key` nullable con índice único. Los valores históricos NULL se conservan. Revisar el índice antes de habilitar canjes; no basta con que exista la opción de versión.
4. **Copias externas:** adaptar `scripts/backup-config.sh.example` fuera del control de versiones. Confirmar WP_ROOT real, carpetas privadas, destino remoto y credenciales de mínimo privilegio; instalar age y configurar AGE_RECIPIENT. La clave privada debe guardarse y probarse fuera del VPS. Los nuevos scripts consideran fallo la ausencia de destino/cifrado: preparar esta configuración antes de activar esos scripts en el servidor.
5. **Restauración completa:** descargar y descifrar un bundle remoto en otro host; verificar el checksum del archivo descargado y ejecutar `restore-bundle.sh` inicialmente **sin flags apply**. Revisar application/system staging, restaurar DB en esquema aislado y copiar selectivamente configuración/carpeta privada a un entorno aislado. Validar login, imágenes, stock, pedido, reembolso, cron y correo. Los flags apply son operaciones del operador: requieren mantenimiento, detener escrituras y un plan de reversión. No aplicar ciegamente `--apply-system-config` sobre `/`. El script no ofrece una transacción atómica entre DB, archivos y sistema.
6. **Cron y correo:** instalar/validar el cron con el usuario PHP adecuado y comprobar ejecuciones vencidas, reservas liberadas, tareas fallidas Action Scheduler y recepción real de avisos de nuevo pedido/fallo de backup. Un exit cero de `wp_mail` no demuestra entrega. Configurar observación externa del sitio y del monitor: si el servidor entero cae, no podrá enviar su propia alerta.
7. **Privacidad:** dar escritura al usuario PHP sobre `BSC_SKIN_QUIZ_PRIVATE_DIR`, fuera del document root. Verificar `bsc_skin_quiz_private_migration_2_done` y ausencia de `bsc_skin_quiz_migration_error`; comprobar que las URLs públicas antiguas no sirven imágenes. Probar eliminación de una rutina con archivo real y vencimiento del token. La retención de las copias externas se configura aparte.
8. **Caché/capacidad:** confirmar bypass real de Cloudflare/Nginx para cookies Woo, usuarios, cuenta, checkout, login, registro, pagos y resultados privados; comprobar dos sesiones diferentes. Hacer carga escalonada en staging con catálogo y checkout, medir p95, errores, PHP workers, CPU, memoria y DB. Los ocho procesos de integración prueban invariantes, no la capacidad del VPS. Separar IA del pool que atiende pagos si la capacidad es ajustada.
9. **CI/CD:** conservar los archivos actuales implica conservar A16/A17. Antes de tu publicación manual, comprobar el SHA servido en origen y tener una reversión ensayada que contemple DB/archivos. No interpretes el check verde existente como prueba completa de checkout. Esta implementación no ejecutó ni alteró ese pipeline.

## Reproducción local y reversión

Con Local iniciado y PHP/INI de esa instalación seleccionados:

```text
npm run lint
npm run test:domain
composer run lint:phpstan
npm audit
composer audit
npm run bundle
```

`tests/production-integration.php` y `tools/test-production-concurrency.js` requieren `BSC_LOCAL_INTEGRATION=1` y el host `bsc.local`. Para los tests E2E seleccionar `PLAYWRIGHT_BASE_URL`, `PW_PHP_BIN` y `PW_PHP_INI`. Antes de repetir pruebas con escrituras, copiar `tests/fixtures/local-audit-guard.php` a `wp-content/mu-plugins/bsc-local-audit-guard.php` **exclusivamente en Local**. Esto bloquea correo/HTTP externo y añade la pasarela sin cobro sólo para `qa.visual` y usuarios efímeros `qa-checkout-*`. La prueba de compra requiere además `BSC_LOCAL_CHECKOUT=1`; la prueba de saldo temporal requiere `BSC_LOCAL_INTEGRATION=1`. Retirar el archivo de mu-plugins al acabar incluso si fallan los tests. Se retiró en esta sesión, el test de compra se omite por defecto y el fixture queda excluido del ZIP. No habilitarlo en producción. Los logs conservan el resultado ya ejecutado.

PHPStan se ejecuta con un trabajador y límite de 4 GB; el bootstrap anterior no conocía correctamente las clases WooCommerce. La antigua baseline sigue en el repositorio como archivo histórico, pero ya no se incluye en la configuración activa. WPCS es una comprobación separada que permanece pendiente.

El backup SQL de Local y el snapshot de archivos anteriores están fuera del webroot en la carpeta de evidencia. `baseline.json` identifica las versiones anteriores de los archivos de texto incluidos en el snapshot; `change-manifest.json` identifica sus diferencias y los archivos nuevos de esta implementación. El snapshot no incluyó mapas CSS ni `composer.lock`: el manifiesto los separa y no atribuye automáticamente sus diferencias de Git a esta tarea. No usar `git reset --hard`: perdería los cambios que ya estaban presentes antes de comenzar. Para revertir, comparar cada archivo con `before/`, restaurar sólo el delta de esta tarea y conservar modificaciones posteriores. No degradar a la lógica anterior de stock/puntos con nuevos movimientos ya aceptados sin conciliarlos primero. No eliminar el índice/ledger para resolver discrepancias: conservar historial y conciliar por pedido.
