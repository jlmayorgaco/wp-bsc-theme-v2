# BSC-045 — Sistema de backups automáticos 3-2-1

## Objetivo
Implementar backups automáticos siguiendo la estrategia 3-2-1: 3 copias de los datos, en 2 medios diferentes, con 1 copia off-site. Incluye backup diario de DB, backup semanal de archivos, retención automática y logs de ejecución.

## Contexto
Actualmente NO hay backup automático del sitio. Esto es un riesgo crítico de negocio. Un script de backup mal configurado o ausente puede significar pérdida total de datos ante un fallo. La estrategia 3-2-1 es el mínimo estándar para producción.

## Archivos a revisar/crear
- Nuevo `scripts/backup-db.sh` — backup solo de base de datos (diario)
- Nuevo `scripts/backup-full.sh` — backup completo: DB + uploads + theme (semanal)
- Nuevo `scripts/backup-config.sh` — variables de configuración (excluir de git)

## Implementación exacta
1. Crear `scripts/backup-config.sh` (no committear, agregar a `.gitignore`):
   ```bash
   DB_HOST="localhost"
   DB_NAME="bsc_production"
   DB_USER="bsc_user"
   DB_PASS="secure_password"
   WP_ROOT="/var/www/html"
   BACKUP_LOCAL="/backups/bsc"
   REMOTE_DEST="user@backup-server:/backups/bsc"  # o S3 bucket
   RETENTION_DAYS=30
   LOG_FILE="/var/log/bsc-backup.log"
   ```
2. Crear `scripts/backup-db.sh`:
   ```bash
   #!/bin/bash
   source /path/to/backup-config.sh
   DATE=$(date +%F-%H-%M)
   mkdir -p $BACKUP_LOCAL/db
   mysqldump -h $DB_HOST -u $DB_USER -p$DB_PASS $DB_NAME | gzip > $BACKUP_LOCAL/db/db-$DATE.sql.gz
   echo "[$(date)] DB backup OK: db-$DATE.sql.gz" >> $LOG_FILE
   find $BACKUP_LOCAL/db -type f -mtime +$RETENTION_DAYS -delete
   ```
3. Crear `scripts/backup-full.sh`:
   ```bash
   #!/bin/bash
   source /path/to/backup-config.sh
   DATE=$(date +%F)
   mkdir -p $BACKUP_LOCAL/full
   tar -czf $BACKUP_LOCAL/full/full-$DATE.tar.gz \
       $WP_ROOT/wp-content/uploads \
       $WP_ROOT/wp-content/themes/wp-bsc-theme-v2
   mysqldump -h $DB_HOST -u $DB_USER -p$DB_PASS $DB_NAME | gzip >> $BACKUP_LOCAL/full/full-$DATE.tar.gz
   echo "[$(date)] Full backup OK: full-$DATE.tar.gz" >> $LOG_FILE
   # Copiar a destino remoto
   rsync -az $BACKUP_LOCAL/full/full-$DATE.tar.gz $REMOTE_DEST/full/ 2>> $LOG_FILE
   find $BACKUP_LOCAL/full -type f -mtime +$RETENTION_DAYS -delete
   ```
4. Instrucciones de cronjob (documentar en README):
   ```bash
   # DB backup diario a las 2 AM
   0 2 * * * /path/to/scripts/backup-db.sh
   # Full backup semanal los domingos a las 3 AM
   0 3 * * 0 /path/to/scripts/backup-full.sh
   ```
5. Agregar `scripts/backup-config.sh` al `.gitignore`.

## Qué NO se acepta como solución
- Backup sin retención automática (se llena el disco).
- Backup solo local sin copia remota.
- Sin log de ejecución.
- Credenciales de DB en el script principal (deben estar en `backup-config.sh`).

## Requerimientos
- Los scripts deben tener `chmod +x` antes de ejecutarse.
- El `backup-config.sh` no debe estar en el repositorio de git.
- Los logs deben ser legibles con fecha/hora de cada ejecución.

## Criterios de aceptación
- El script de backup DB se ejecuta sin errores y genera un archivo `.sql.gz`.
- El script de backup full genera un archivo `.tar.gz` con uploads y theme.
- Los archivos viejos (> 30 días) se eliminan automáticamente.
- El log registra cada ejecución con fecha/hora y estado.
- Existe copia remota (rsync o equivalente).

## QA manual
- Ejecutar `bash scripts/backup-db.sh` manualmente → verificar archivo generado.
- Verificar el log → tiene entrada con fecha/hora.
- Ejecutar `bash scripts/backup-full.sh` → verificar archivo `.tar.gz`.
- Verificar que el archivo contiene uploads y theme (con `tar -tzf`).
- Esperar un día → verificar que el cronjob se ejecutó (revisar log).
